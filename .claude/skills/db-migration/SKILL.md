# Миграции без простоя

Во время деплоя старый контейнер ещё работает на новой схеме, а открытые вкладки живут на старом фронте. Поэтому каждая миграция совместима со старым кодом.

## Можно сразу (расширение)

- `create table`, `add column` с `default` или nullable, новый индекс. Раннер выполняет миграции в транзакции, поэтому `create index concurrently` в нём не работает: на таблицах до ~1 млн строк обычный `create index` занимает секунды, для больших — обсуди с владельцем.
- Новая таблица для новой фичи за флагом.

## В три релиза (переименование, смена типа, удаление)

1. **expand**: новая колонка/таблица, код пишет в обе, читает из старой.
2. **migrate**: перенос данных (миграцией или фоновой задачей), код читает из новой.
3. **contract** (через ≥ 1 день, с «да» владельца): миграция с первой строкой `-- contract`, удаляет старое. Перед ней `scripts/ops.sh backup-now`.

`scripts/check-contract.mjs` не пропустит `drop`/`rename`/`alter … type` без `-- contract`; хук не даст поменять уже закоммиченную миграцию.

## Порядок

1. `apps/<app>/migrations/000N_что_делаем.sql` (следующий номер).
2. Локально: Postgres (`docker run -p 5432:5432 -e POSTGRES_HOST_AUTH_METHOD=trust postgres:17-alpine` или системный), `DATABASE_URL=... pnpm --filter <app> dev` — миграция накатится при старте, посмотри лог.
3. Тест или e2e, который трогает новую схему.
4. Выкатка (скилл `ship`). Миграция падает → контейнер не стартует → Kamal не переключает трафик → прод на старой версии. Смотри `scripts/ops.sh logs`.
